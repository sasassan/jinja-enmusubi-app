# 「神社ナビ」拡張仕様 ギャップ分析レポート

対象: `神社アプリ` プロジェクト（公開済み「神社御縁」）の既存実装 vs 提示された「神社ナビ」拡張仕様
分析範囲: 仕様レビュー・現行コード/DB調査のみ。実装は行っていません。

---

## 0. 調査で確認した現状（前提の補正）

ユーザー提示の「現状」記述に対し、実コード調査で以下の重要な差分を確認した。分析全体の前提として明記する。

- **DBスキーマは仕様が想定するより先行している**: `supabase/migrations/20260907120000_initial_schema.sql` には `favorites`, `visits`, `visit_photos`, `digital_goshuin_settings`, `digital_goshuin`, `admin_allowlist` が**既にテーブルとして存在**する（RLSポリシーも一部適用済み）。ただしこれらに対応するUI・APIロジック・Storage連携は**一切実装されていない**（`src/app`, `src/components` に該当ページ・コンポーネントなし）。→ 「スキーマは先行、機能は未着手」というギャップ。
- **既存の重大な不整合（要修正）**: `src/lib/shrines.ts` は Supabase から `latitude`, `longitude` の個別カラムを取得しようとしているが、実スキーマは PostGIS の `location geography(point,4326)` のみで緯度経度カラムを持たない（`rg` で確認、`latitude|longitude` は migration/seed 双方に不在）。このため本番 DB 接続時、このクエリは該当カラムが存在せず失敗するか常に `null` を返し、`getShrineData()` の `if (row.latitude == null ...) return null` によって**全件フォールバック（デモデータ表示）に落ちている可能性が高い**。現在地検索・現行の「DB接続済み」という前提そのものに疑義があり、Phase 1 着手前に要検証。
- **認証機能は未実装**: `@supabase/supabase-js` は依存にあるが、`src/` 内に `auth.`, `signIn`, `signUp` 等の呼び出しは0件。`@verdent/auth-js` も未導入。`profiles`, `admin_allowlist` テーブルはあるが接続するコードがない。→ 仕様のMVP12(ユーザー登録)・20(管理画面)は「土台のみ」。
- **地図ライブラリは未導入**: Leaflet/Mapbox/Google Maps JS SDK のいずれも未導入。現在地→距離順ソート＋外部Google Mapsへのリンク（`ShrineExplorer.tsx:326`）のみで、**アプリ内地図表示は0**。仕様のMVP9(地図表示)は完全に新規。
- 御朱印帳は `/goshuincho` にデモデータのみで表示されており、`visits`/`digital_goshuin` テーブルとは未接続。

以降のギャップ分析・差分表・フェーズ計画はこの実態を前提にする。

## 1. ギャップリスト（重要度付き）

凡例: 🔴 Blocker級（仕様確定なしに着手すると手戻り必至） / 🟠 高（初期に方針決定すべき） / 🟡 中（フェーズ内で決めれば足りる）

### 🔴 Blocker級

1. **既存コードのDBスキーマ不整合**（上記0節）。緯度経度の取得方法を `location`（PostGIS）から導出する形に修正しないと、現在地検索・地図機能すべてが土台から崩れる。設計判断: `ST_X(location::geometry)`/`ST_Y(...)` で都度算出するか、生成列（generated column）で `latitude`/`longitude` を追加するか。
2. **写真アップロードの保存先・容量・処理方針**: Supabase Storageのバケット構成（public/private分離）、ファイルサイズ上限、リサイズ/EXIF位置情報除去（重要: 参拝記録写真にGPS EXIFが残ると「外部非公開」方針と矛盾しうる）、対応形式が未定義。
3. **地図ライブラリ選定とコスト**: Google Maps JS API（従量課金・APIキー管理）/Mapbox（無料枠+従量）/Leaflet+OSM（無料・商用可・オフラインタイル不可)。PWA・将来のネイティブ移行を考えると選定基準（コスト・オフライン対応・日本語POI充実度）が未確定。
4. **管理画面の認証・権限設計**: `admin_allowlist` テーブルは存在するが、誰が管理者かを判定するロジック・ログインフロー・RLSでの管理者専用書き込み権限ポリシーが未実装。CMSの認可設計がないと神社データ拡充が進められない。
5. **神社データ拡充の運用フロー（出典収集・著作権）**: 「実在情報のみ、架空データ禁止」という制約下で、誰が・どの手順で・どの一次情報から新規神社データを追加するか。写真の著作権・利用許諾（神社境内写真の撮影・掲載可否は神社ごとに異なる）が未定義。ビジネス判断が必要（4章参照）。

### 🟠 高

6. **GPS参拝判定の精度基準**: 「神社のGPS付近」の許容半径（既存スキーマでは `digital_goshuin_settings.radius_meters` が25〜1000mでcheck制約済みだが、デフォルト値・神社ごとの適正値・スプーフィング対策（モックロケーション検出、連続する非現実的移動の検知）の方針が未定義）。
7. **プライバシー・法令対応**: 位置情報を扱うため利用規約・プライバシーポリシーの明文化が必須（個人情報保護法・GPS取得の同意フロー）。RLSは「他ユーザーからの非公開」は担保できるが、「法的に必要な同意取得UI」は別途必要。
8. **アカウント削除・データエクスポート**: 現行 `profiles` テーブルのCASCADE削除は `auth.users` 削除に連動するが、`visit_photos`（Storageの実ファイル）はDBレコード削除だけでは消えない。GDPR的要件（該当する場合）や日本の個人情報保護法観点でのエクスポート機能要否。
9. **神様検索の入力UX**: フリーテキスト（読み仮名・別名・異体字表記ゆれ「素戔嗚尊/素盞嗚尊」対応）か選択式チップか。既存実装はチップ式AND絞り込みのみでフリーテキストの表記ゆれ対応なし。全文検索(pg_trgm/tsvector)導入の要否。
10. **デジタル御朱印デザインの供給**: 神社ごとの紋章・デザインアセットを誰が作成するか（イラスト外注/AI生成/簡易テンプレート+神社名のみ）。全神社分を用意するコストが非現実的な場合、MVPでは「共通デザイン+神社名」で妥協するかの判断が必要。
11. **既存デザインシステムとの統合方針の矛盾**: 現行実装は「伝統色トークン」ベースの和風デザインシステムを構築済み（コントラスト修正タスクも進行中）。仕様は「和風に寄せすぎない、筆文字・過剰な鳥居・派手な赤色を避ける」と明記しており、**方向性が正面から矛盾**する。既存デザインシステムを刷新するか、仕様側の表現を「現行の落ち着いた伝統色トーン」で満たせると解釈するかの判断が必要（4章参照）。
12. **パフォーマンス設計（将来の数百〜千件規模）**: 現行は全件取得+クライアント側フィルタ（`ShrineExplorer.tsx` 想定）。数百件規模になった場合、サーバーサイドページネーション・PostGIS空間インデックスを使った半径検索（`ST_DWithin`）・複合GINインデックス（多対多タグ検索）への切替が必要。現状指数は `location` にgistインデックスのみで、系統/御利益検索用の複合インデックスは未検討。
13. **MVP20項目の優先順位と移行パス**: 現行実装（検索・カード・詳細シート・御朱印帳デモ）と20項目の対応関係が未整理。「地図」「認証」「参拝記録」「管理画面」は完全新規かつ相互依存（認証→参拝記録→御朱印帳→履歴の順で積む必要がある）。

### 🟡 中

14. 「人物→神格化→関連神社」の検索導線のUI設計（既存の神様検索フローとの統一感）。
15. 御利益表現の適正化ガードレール（「一般に○○の神として信仰される」等の文言）を管理画面の入力バリデーション/ガイドラインとして強制するか、単なる運用ルールに留めるかの決定。
16. AI機能（将来）は現時点で仕様上「将来」と明記されているため優先度低だが、データ構造（sources, last_verified_at）がAI回答の裏付けとして再利用可能な設計になっているかの確認は今のうちに行う価値あり。
17. 外部地図アプリ連携（「ここへ行く」）は実装済みだが、iOSでのApple Maps分岐（現状Google Maps固定URL）は要検討。
18. オフライン対応（PWA）の範囲: 地図タイルのキャッシュ、参拝記録のオフライン下書き→オンライン復帰時同期、のいずれまで対応するか。
19. `shrine_deities` の `role` enum（principal/enshrined/co_enshrined/associated）は仕様の「主祭神/相殿神・配祀神・合祀神」の区別要件をほぼ満たすが、日本語表示ラベルとの対応表整備が必要。
20. 通知機能の有無（未定義・仕様に記載なし）。参拝記録の「思い出」通知等を将来検討するか明記が必要。

## 3. 段階的実装計画案

各フェーズは「1〜数タスクで完結」する粒度。フェーズ間の依存関係（認証→参拝記録→御朱印帳の順）を踏まえた並び。

### Phase 0: 基盤修正・検証（着手前必須）
- タスク: `shrines.ts` の緯度経度バグ修正（`location`から`ST_X/ST_Y`抽出、またはビュー/生成列追加）。実DB接続で `source: "db"` が実際に返るか検証。
- 検証基準: ローカル/検証環境で本番相当のSupabase接続時、`getShrineData()` が `fallback` ではなく `db` を返し、既存4神社が正しい緯度経度で現在地検索に反映されること。

### Phase 1: DB拡張＋検索強化
- タスク: 神様表記ゆれ対応（別名/読み仮名によるあいまい検索、`pg_trgm`導入検討）、地域検索の市町村単位・半径検索(`ST_DWithin`)実装、系統/御利益検索用インデックス最適化。
- 検証基準: 「素戔嗚尊」の別名・読み仮名でヒットする。「福岡県」+「50km以内」の複合検索が正しい結果件数を返す。既存4神社データでリグレッションなし。

### Phase 2: 地図機能
- タスク: 地図ライブラリ選定確定（ビジネス判断待ち、4章参照）→導入、神社マーカー表示、現在地表示、検索条件連動フィルタ、マーカータップ詳細ポップアップ。
- 検証基準: 検索結果が地図上に正しくマーカー表示され、フィルタ変更でマーカーが即時更新される。モバイル実機（またはモバイルビューポート）でタップ操作が機能する。

### Phase 3: 認証基盤
- タスク: Supabase Auth（メール/Google等）導入、`profiles`連携、ログイン/ログアウトUI、セッションガード。
- 検証基準: 新規登録→ログイン→ログアウト→再ログインが一連で動作し、`profiles`レコードが正しく作成される。未ログイン時にお気に入り/参拝記録操作がログイン誘導される。

### Phase 4: お気に入り
- タスク: `favorites`テーブル接続、一覧UI、距離/神様/系統/御利益/地域での絞り込み。
- 検証基準: ログインユーザーが神社をお気に入り登録/解除でき、一覧に正しく反映される。RLSにより他ユーザーのお気に入りが見えないことを確認。

### Phase 5: 参拝記録（GPS+写真）
- タスク: Storageバケット設計（EXIF除去・サイズ制限含む）、参拝記録フォーム、GPS取得・距離検証、`visits`/`visit_photos`書き込み。
- 検証基準: 神社近傍でGPS取得→記録作成→写真アップロード→`visits`テーブルに正しく保存。範囲外では「参拝済み」フラグが立たないことを確認。プライバシーポリシー文言がUI上に表示される。

### Phase 6: デジタル御朱印・御朱印帳
- タスク: GPS判定成立時の`digital_goshuin`発行ロジック、御朱印帳UIの実データ接続（新旧/地域別ソート）、デザインアセット供給方針の確定・適用。
- 検証基準: Phase5の参拝記録から御朱印帳に自動反映される。「公式発行と誤認されない」表記がUI上に明示されている。既存デモページ`/goshuincho`のデモ表示から実データ表示への切替が確認できる。

### Phase 7: 参拝履歴
- タスク: 参拝済み神社の一覧/地図表示、検索結果での「参拝済み/未参拝」バッジ。
- 検証基準: Phase5-6のデータを基に、検索結果・地図・一覧すべてで参拝済み状態が一致して表示される。

### Phase 8: 管理画面（CMS）
- タスク: `admin_allowlist`ベースの認可、神社/神様/系統/御利益/人物CRUD、由緒/写真/出典登録フォーム。
- 検証基準: allowlist外ユーザーがアクセス拒否される。管理者が神社データを追加→公開設定後、フロント側検索・地図に即時反映される。

### Phase 9: 統合検証・アカウント管理
- タスク: アカウント削除フロー（Storage実ファイル削除含む）、利用規約/プライバシーポリシーページ、全フェーズの結合テスト。
- 検証基準: アカウント削除で`profiles`・`visits`・`visit_photos`（Storage含む）・`favorites`・`digital_goshuin`が正しく削除/匿名化される。主要ユーザーフロー（検索→地図→参拝→御朱印帳）がE2Eで一連通過する。

## 4. ユーザー（Manager）決定が必要な事項

以下はManagerの承認済み方針（品質最優先・承認不要）の範囲を超え、ビジネス判断・外部コスト・ブランド方針に関わるため明示的にリストアップする。

1. **地図ライブラリと外部APIコスト**: Google Maps JS API（利用量に応じた課金・APIキー管理）/Mapbox（無料枠あり・従量）/Leaflet+OpenStreetMap（無料、商用利用可、日本語POI精度は劣る場合あり）のいずれを採用するか。予算上限の有無。
2. **神社データの出典と写真の調達方針**: 実在神社データを何件・どの地域まで拡充するか、一次情報（神社公式サイト等）の収集を誰が担当するか、掲載写真を自前撮影/フリー素材/神社への許諾取得のいずれで確保するか（境内撮影・掲載には神社側の許諾が必要な場合がある）。
3. **既存デザインシステム（伝統色トークン・和風方向性）と仕様の「和風に寄せすぎない」方針の整合**: 現行デザインを維持し仕様側の表現を「落ち着いた伝統色」で満たすと解釈するか、仕様に合わせてデザイン刷新（トーン変更）を行うか。
4. **デジタル御朱印デザインアセットの調達方法とコスト**: 神社ごとの紋章/デザインを外注イラストで用意するか、AI生成素材で代替するか、MVPでは共通テンプレートに留めるか。
5. **神社側への公式許諾取得の運用**: 「将来的に神社ごとにデジタル御朱印の公開・発行設定を管理」する機能はDB上は準備済みだが、実際に神社側へ許諾を取りに行う運用（誰が・いつ・どの神社から）は事業判断であり技術範囲外。
6. **法務対応（利用規約・プライバシーポリシーの作成主体）**: 文言のドラフトは支援可能だが、最終的な法的レビュー・公開判断はManager/事業側の責任範囲。
